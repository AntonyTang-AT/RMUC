# 单体建议为什么显得笼统，以及如何量化

日期：2026-09-27。复现：在项目根目录运行 `python eval/audit_unit_recommendations.py`；机器结果写入 `out_m2/unit_recommendation_quality_audit.json`。只读现有比赛数据，取赛程顺序最早的 8 局，红蓝双方都算；每 3 秒一条建议，在精确 `t+3` 和 `t+10` 回放状态上核对。整局为 bootstrap 单位，避免把同一机器人相邻帧误当独立样本。

## 目前为何笼统

`worldstate/unit_state.py::derive_unit_guidance` 确实逐实体产生建议，也带有动作、目标区、第一步、触发/取消条件和证据字段；但它当前主要是规则模板，不是针对单台机器人计划出来的控制命令：

- 大量单位使用“暂留当前区域”“保持掩护等待信号”等不要求改变位置的通用动作；输出缺少简短、可核验的明确对象和任务结果。
- 进攻类建议没有明确敌方单位 ID 时只能说“目标仍可确认”，不能把推测的最近敌人包装成正在攻击的对象。
- 功能区路由可以给合法的第一步，但当前撤退目标主要按图最短路/相邻区选择，没有把速度、路线耗时、危险程度和友军支援纳入排序。
- 置信度尚未校准。证据来源虽然有 `source`，显示层还没有统一展示“实测 / 地图推导 / 几何推断 / 未知”的可信等级。
- 数据库没有实际下发的移动、瞄准、开火或任务指令。故“机器人后来到了建议区域”不是“控制器执行了建议”，更不是“建议造成了收益”。

8 局审计里每侧约 5.7–6.0 千条可核验单位建议，却只有 5 种动作文本。红方主要是“暂留”2266、“等待攻击信号”2120、“保持防区”673；蓝方分别为 2918、1968、418。约 95% 建议第一步仍是当前区域。当前建议的区分度主要是机器人/当前位置的重复规则分类，任务上下文不足，因此看起来像给整类机器人重复同一句话。

## 本轮输出层改进

`worldstate/narrative.py` 为每台我方机器人生成 `advice_text`，按“现状—建议—依据—满足条件—停止条件”组织；建议卡片也分别展示首步区域、目标区域与核验方式。此前把 `current_state` 直接当作建议理由的问题已修正，统一显示为“依据当前观测”。敌方预测保留在独立字段，只对身份可对应且未被抑制的路线显示候选；同兵种有多台而预测无法按 ID 对齐时，不把编组预测冒充单车路线。

回放中的全局文字压缩为“现况、关键预测、建议”三段，特殊事件和战术判断并入现况。它目前是 `structured_evidence_template` 规则/证据模板，不是 Qwen/JEV 在线生成；结构化预测和核验字段仍保留。此次调整改善了阅读和事实归属，不会改变旧的动作质量审计指标，也不能解决目前约 95% 建议首步留在原区、建议并未实际下发控制器的问题。

## 可复现的 per-entity 建议记录

建议持久化为不可变记录；同一个 `game_id + side + entity_id + issue_time + policy_version` 只能有一条。每个事实字段都使用统一的值、来源、是否可观测结构，不要把观测与推测揉在一句话里。

| 字段 | 要求 |
|---|---|
| 身份与时间 | `game_id, side, entity_id, unit_type, issue_time, policy_version`；保存当时的感知快照哈希。 |
| 现状 | 位置/功能区、速度向量、车头朝向、HP比例、生存状态、弹量/热量、可见目标、任务/资源携带。每字段标 `observed`、`derived`、`inferred` 或 `unknown`，并带来源和时间戳。 |
| 明确动作 | 受限枚举，例如 `hold_cover`、`retreat`、`advance_to_objective`、`attack_visible_target`、`guard_facility`、`return_resource`、`wait_for_confirmation`。另给面向人的短句。不得把“预测”写成我方动作指令。 |
| 路线 | `from_zone`、`first_step_zone`、`goal_zone`、`path_zones`；留在原区时显式写 `hold`，否则每一步都必须在对应兵种的通行图上合法。附距离/估算耗时及速度来源。 |
| 目标与理由 | 单位目标使用 `target_entity_id`；设施用设施 ID。理由最多两条，绑定实际证据字段和阈值，例如“HP 24%，低于撤退阈值 30%”“敌方英雄在 5.2m 内且持续可见”。没有对应观测就写“未知”，不补故事。 |
| 条件 | 可计算的 `trigger`、`cancel` 和有效期。取消后重算，不继续展示过期计划。 |
| 置信度 | 置信度属于动作/路线预测结果，不能由 LLM 自评。按动作类别在验证集上用真实事件/行为响应拟合并校准；展示校准后概率和适用范围。没有标签时显示“未校准”。 |
| 核验 | `check_at_seconds`、主指标、基线策略、分母/缺失原因。位置类建议至少同时检查 3 秒进度和 10 秒达成；攻击建议用发弹/命中事件，资源建议用携带/兑换等直接状态。 |

### 信息来源分层

- **可直接观测**：本方位置、HP/maxHP、枪口/车体运动、弹量累计值、发弹事件、受击/目标生命变化（按系统实际订阅权限）。
- **地图推导**：XY 映射出的功能区、由已验证通行图算出的邻接路线/距离。它们是计算结果，不能标成传感器实测。
- **几何推断**：可见敌人在本方射程近似范围内、可能交战对象等；输出须注明推断及其简化假设。
- **未知**：无实际任务/货物字段时，工程师是否去挖矿、携带物品和计划返程；无可靠目标 ID 时攻击目标；雷达看不到的敌方状态。未知既不是“否”，也不是可用于高置信建议的事实。

## 指标分层与当前证据

| 层级 | 量化指标 | 当前是否能算 | 解释 |
|---|---|---|---|
| 约束正确性 | 首步路线合法率、路线可达率、未知字段误断言率、阵亡单位建议率 | 合法率能算；其余部分可算 | 安全门槛，不是效果分。 |
| 建议是否可执行 | 指令/动作与建议的一致率；从发出到动作启动延迟 | **不能直接算** | 库里没有控制器的实际命令/任务日志。事件表的 `发弹` 可核对发生了射击，但不能证明开火由建议触发。 |
| 位置响应代理 | 对移动建议测 `t+3` 目标首步命中、目标距离缩短比例、合法路径进度；`t+10` 曾到/最终到达率。保持建议对比 stay-put；移动建议只在相同移动子集上与 stay-put 命中率/距离基线比较 | 能算 | 表示观测轨迹是否朝建议走，不能称执行吻合或因果收益。按整局做配对 bootstrap，并按红蓝、动作、兵种报告。 |
| 可观察结果代理 | 建议后 3/10 秒的 HP、设施 HP、资源/金币变化、目标状态改变；按同局同阶段相似状态与当前规则策略比较 | 能算一部分 | 仅相关性；金币净额、HP 变化都受多方动作影响。没有反事实设计不能宣称收益。 |
| 决策收益 | 胜率/目标收益因建议而变的差值 | **不能从现有日志识别** | 需要命令日志、冻结策略版本和可比对照或可信反事实评估。 |

主判据不得只是 100% 合法率。建议先把部署质量门槛设为：**安全约束全部通过**，并且相较同状态 stay-put/现有规则，按整局配对 bootstrap 的 `t+10` 路径进度或任务完成差值为正、95% 区间下界不低于 0；同时分红蓝看方向一致。若 CI 跨 0，则报告“尚无优于基线证据”，而不是把准确率或局部成功率当提升。当前 8 局属于早期诊断，正式门槛需冻结新对局做盲测。

## 现有比赛的实测结果

使用当前 3 秒建议节奏、首 8 局、仅存活单位：

| 指标 | 红方视角 | 蓝方视角 | 红蓝等权 |
|---|---:|---:|---:|
| 建议第一步合法 | 100% | 100% | 100% |
| 全建议：3 秒后观测区命中建议第一步 | 75.76% | 71.14% | 73.45% |
| 同一批锚点：保持当前区域基线 | 78.27% | 74.52% | 76.39% |
| 非原地建议数 | 230 | 304 | 534 |
| 非原地建议：3 秒实际到建议区 | 4.35% | 4.93% | 4.68% |
| 非原地建议：3 秒留在原区（对照） | 66.96% | 72.04% | 69.84% |
| 非原地建议：3 秒内朝目标区中心靠近 | 56.52% | 59.54% | 58.03% |
| 非原地建议：10 秒到目标区 | 3.52% | 4.70% | 4.19% |
| 非原地建议：10 秒合法路线缩短至少一跳 | 4.26%（n=188） | 6.06%（n=231） | 5.25%（n=419） |
| 暂留建议：10 秒仍在原功能区 | 65.72% | 61.88% | 63.76% |

按整局配对 bootstrap（8 局，固定种子，红蓝分别计算），“全建议”比 stay-put 的 3 秒区域命中差：红方 **−2.78 个百分点**，95% CI **[−6.17, −0.16]**；蓝方 **−3.89 个百分点**，95% CI **[−9.18, −0.84]**。等权点估计约 −2.94 个百分点。两侧都未显示建议优于基线。

多数建议是留在当前区，因此全量留区命中不是好策略增益指标；它只暴露出留区建议的高惯性。非原地建议里，更多单位确实向目标方向移动，但 3 秒内跨入新区很少。不能把这点解释为采用了建议，亦不能推断延长时间后必会到达。应在 `t+10` 继续按物理可达时间检查目标区和路线进度；真实指令日志出现前，所有结果都标“位置响应代理”。

10 秒新增指标按建议路线与通行图计算最短功能区跳数：只有起点和目标都可达的样本进入分母；若实际区域到目标的最少合法跳数小于发出建议时的跳数，记为“路线缩短”。两侧合计 419 条可评分移动建议中，22 条（5.25%）在 10 秒内至少缩短一跳；22/525（4.19%）到达目标区。这个结果说明日志里的轨迹很少朝规则建议路线推进，但**不能解释为建议失败或单位拒绝执行**：数据库没有保存建议是否发送给控制器、控制器是否接受，也没有记录比赛当时的真实任务命令。必须把它称为“观测轨迹与建议路线的一致性代理”。

这次增补不会把“10秒留在原区”与移动建议的目标到达率拿来宣称胜负。二者适用动作不同；对留区建议报告区域保持率，对移动建议报告目标到达率、合法路径进度与覆盖率，并分动作/兵种/阵营呈现。更高层的收益评估仍需实际命令日志和冻结版本对照。

## 下一步落地顺序

1. 先把建议卡片收敛到“现状（实测/推导/推断/未知）—建议做什么—目标/路线—为什么—什么时候撤销—何时核验”六项；只给有可核验目标的机器人输出动作，其余明确写“暂不建议移动，等待什么信号”。
2. 不给所有单位同一兵种套固定段落。使用机器人 ID 和实时状态生成动作，动作类型/建议理由则需从可观测状态复现；先区分哨兵防守、低血量撤退、工程携带返还、明确发弹压制等已被证据支持的情形。
3. 当前攻击用的“可能目标”不能直接作为攻击目标 ID。事件表有“发弹/受击/飞镖命中”，可做行为结果代理；也可增加实际控制器日志，记录 `issued_action_id, target_id, controller_accept/reject, command_time, observed_start_time`。
4. 现有日志先报告 `t+3` 建议区响应、`t+10` 目标到达/合法路径进度和覆盖率；不能把观察到的动作当成控制器执行。未来接入命令日志后，再与 stay-put、相同可达条件的规则建议做成对照。若某类建议覆盖率很低，要显示“不足以打分”，不能以其他类别填补。
5. 未来收益试验需在新比赛上冻结一版策略，红蓝双方都跑；比赛为统计簇。再用随机/分时启用的安全策略试验或高保真反事实仿真测 HP、设施和胜率收益，避免以之后发生的变化冒充因果。
