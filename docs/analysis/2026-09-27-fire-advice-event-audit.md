# 开火建议的事件响应代理审计

复现命令：`python eval/audit_fire_advice_event_proxy.py`。原始输出：`out_m2/fire_advice_event_proxy.json`。本审计用正式时间序最早的 8 局，红蓝各自视角，3 秒决策锚点；对“继续压制”类建议检查发出后的 `(t, t+3]` 和 `(t, t+10]` 是否出现同一 robot ID 的 `发弹` 事件。再与同期同队、同兵种、但没有收到该类建议的单位作描述性对比；置信区间按整局重抽样。

此前把 3 秒英雄低率当作“规则不适用”属于窗口选择造成的误读。对英雄的 42mm 发弹事件，按全库连续射击间隔统计，中位间隔为 **7 秒**，相邻两次间隔不超过 3 秒的仅 **8.63%**；因此 3 秒未再发弹不能判定建议不适用。以 10 秒看，英雄发弹建议组为红 25/41（60.98%）、蓝 29/45（64.44%），略高于同期同队同兵种其他建议参考组的红 51.82%、蓝 56.16%。这是状态持续的相关性结果，仍非策略收益。

同时检查了数据库是否漏把英雄开火记成其他事件：赛事协议明确规定 `发弹` 的类别含 `42mm`。在全部 **613 局**中，1147 个出现过英雄累计42mm弹量增长的“局-阵营-机器人”组全部也至少有一条 `发弹/42mm` 事件；不存在弹量增长但完全没有42mm事件的组，也不存在事件单独出现的组。两个来源的总量为 23,866 次弹量正增量与 23,869 条事件，相差 3；首 8 局两者均为 389。故数据不足以解释英雄3秒差异为系统性事件漏记，主要限制是3秒窗过短、事件不含目标关联。

核对代码发现，`continue_attack_visible_target` 来自“最近观测到本方发弹”加“存在显式瞄准目标或射程内最近可见敌人”；其中 geometry nearest 是候选目标，射击事件并未绑定目标 ID。此前证据列表把该 ID 标成当前观测，容易误解成“已证实攻击目标”。因此保留触发和评分规则，只改英雄卡片措辞：刚有 42mm 开火记录；若无显式瞄准目标，附近敌人明确标成候选目标，并提示继续跟踪、下次开火前重新确认目标和自身安全；几何推断 ID 的 provenance 标为 `visible_geometry_inference`。同时仅当存在显式传感器目标时才导出 `attacking_target` 供地图画攻击连线；最近敌人继续保留在 `possible_target`，不再伪装成弹道目标。没有声称事件能确认子弹打向该候选目标。

在首 8 局双侧回放的 **86 条英雄“继续攻击”建议**里，0 条来自显式目标 ID，86 条都是射击信号加最近可见敌人几何候选。这证实先前将目标 ID 写成“当前观测”的来源标签有误；问题在目标关联字段，而不是“42mm事件没写进发弹表”。修正后，当前发弹事实与候选对象分别呈现。

## 指标边界

- 这里是**事件响应 / 行为一致性代理**：建议以后发生发弹事件的比例。它不是建议准确率，也不是实际控制器执行率。
- 对比组含其他任务和状态；即使按兵种分层，仍然没有控制当前目标、射程、弹药、冷却、驾驶指令等状态，因此不是随机对照。
- 事件中的发弹记录没有攻击者到目标的关联。建议记录中的目标 ID 若来自“附近最近敌人”，只代表可见候选目标，不能证明子弹打向它；也无法把受击归因给这条建议。
- 同一个实体在一局有连续锚点，标准误按比赛局抽样，不能按机器人帧数扩增样本独立性。8 局仍是小样本诊断。
- 若要严格评估建议：先记录实际的 `issued_action_id / target_id / command_time / accept_or_reject / start_time`，再量动作吻合和响应延迟；评估建议的因果收益还需要随机或可靠反事实设计。现有发弹事件适合做在线校准与异常预警，不能取代控制命令日志。

## 对单体建议的直接改进依据

1. 对英雄保留当前开火分支，但把几何选出的最近敌人明确显示成“候选目标”；有明确传感器瞄准目标时才显示“已指定目标”。
2. 继续保留3秒事件行为和10秒事件行为的独立分母。英雄3秒再发弹率受42mm射击节奏影响，不能作为规则准确率或适用性门槛；10秒率仍只作行为响应参考。
3. 界面把“建议动作”“后续出现的事件”“是否收到控制器确认”分成三栏。现在只具备第一、第二项；控制器确认应明确显示“无日志，未知”。
